## 前提と限界（先に読んでください）

1. **パッケージ自身の手順との関係。** `reviews/CLAUDE_COUNTER_REVIEW_PROMPT.md` は、事前条件として「`reviews/codex/REVIEW.md` が実在し、状態が `codex_complete` であること。満たさなければ停止して報告」と定めている。実際の状態は `codex_review_recorded`（人間の採否は pending）で、**この条件は満たされていない**。今回は利用者の依頼により実施したが、本報告書は同手順のゲート通過とは見なせず、`review-state.json` や ISSUES は一切変更していない。
2. **Phase A（先入観なしの独立審査）は成立していない。** 設計文書（`ISSUES.md`、`DECISIONS.md`、`REVIEW_LOG.md` など）自体にCodexの指摘が織り込まれており、読む前に切り離せなかった。Codexの `REVIEW.md` は R2-01・R2-02 のみ本文を読み、R2-03〜05 は ISSUES/REMEDIATION の要約までしか確認していない。
3. アプリ本体が存在しないため、実行できる試験は文書検査スクリプトだけである。以下の「再現」はすべてその範囲の再現で、製品挙動の再現ではない。
4. 実行環境はこの会話のクラウド環境。zipは新規フォルダーに展開し、改ざん試験はすべてコピー上で行った。

## 指摘事項

### CR-01（High・設計）最初の実装範囲では、製品の中心価値を検証できない

- 根拠: `docs/01-product/PRD.md` §2 は利用ストーリーを「…⑦承認後にVaultを更新 ⑧次の別問題で再利用 ⑨記憶有無で効果を測定」で閉じる。一方 `docs/07-delivery/NEXT_STEPS.md` の推奨初回範囲は「Vault読取→検索→候補→検証証拠→差分確認まで」で、Vault書込と再利用効果を含まない。Vault書込は ADR-008（未決）・TEST-KB-010（未実施）に依存し、「未検証writerは適用不可」とされる。
- 反論: 価値仮説の核は「検証済み知識の再利用で未知タスクの成果が改善する」ことだが、書込が無効な最初の実装では ⑦〜⑨ に到達できない。しかも Vault書込の成否を左右する実験（`VERIFICATION_PLAN.md` §3 の PoC A「AIが更新中に人が編集」、PoC B「worker kill後の重複なし復旧」）は、アプリ本体が無くても使い捨てのスクリプトで実施できる。ADR-018 / G5-D / `POST_IMPLEMENTATION_VALIDATION.md` はそれらを「実装後」に回しており、**実現可能性の調査（spike）と実装後の受入試験を同一視している**。
- 期待: 実装許可（I）の前に、アプリ非依存の spike（書込競合・ローカルモデルの実用性・5名の聞き取り）を置く。聞き取りは文書でも H-pending と認めている通り実装なしで可能。
- 影響: Critical の ISSUE-001（書込）と High の ISSUE-005（ローカルモデル）が未検証のまま、設計だけが改版され続ける恐れ。
- 確度: 文書の記述同士の比較に基づく設計上の反論。誤りがあるとすれば、「最初の実装は読み取り専用の候補生成で十分に価値が出る」と人間が判断した場合のみ。

### CR-02（High・設計）「job単位で単調に増えるtaint」と想定利用者の組み合わせで、Cloudは事実上使えない。ローカル推論の合格基準も未定義

- 根拠: `EXECUTION_CONTRACTS.md` §1 は「一度でも非public又はunknown入力に触れたjob全体をCloud不可」とし、要約・匿名化でも下げない。PRD の想定利用者 P-01 は「顧客データを公開クラウドへ送信したくない」SQL/VBAの実務者。
- 反論: 想定する仕事の大半が顧客由来の入力に触れる以上、実質は「全面ローカル」になる。製品の可用性は P0「機密タスク用の最小推論経路」の品質に完全に依存するが、「最小」に合格基準（例: 架空SQL N件のうちM件で期待結果）が定義されておらず、TEST-AI-002 は「能力確認も含む」とあるのみ。PRD は「成立しなければP0未達でNo-Go」と書くが、何をもって成立とするかが決まっていない。
- 期待: 実装前に、ローカル推論の合格基準（件数・正答率・許容時間）を人間が決めて固定する。この種の閾値は「実験前に決定する」と文書自身が述べている。
- 影響: 設計承認（G5-D）後に初めて「ローカルモデルでは使い物にならない」と判明すると、安全設計全体の前提が崩れる。
- 確度: 設計上の反論。保守的な規則（分類の引下げ機能を初期対象外とする）は文書に明記された意図的な選択である。

### CR-03（High・仕様欠落）認証系のAPIがなく、認証を所有する要件もない。画面に必要な一覧系APIも欠けている

- 再現（`docs/03-architecture/API_CONTRACT.md` の検索）:
  - 認証関連の語は冒頭の説明文のみ。「local pairingでsessionを確立」「変更APIはsession束縛のCSRF token」と述べるが、エンドポイント表に **pairing・セッション発行/更新/失効・ログアウト・CSRFトークン取得のroute がない**。クライアントがCSRFトークンを得る経路が定義されていない。
  - 画面側の必要に対して不足するroute:
    - SCR-02「仕事一覧」→ `GET /jobs`（コレクション）がない（`GET /jobs/{job_id}` のみ）。
    - 知識候補の審査（`KNOWLEDGE_MODEL.md` の「候補審査画面の専用経路」）→ 候補一覧を返すrouteがない。
    - SCR-09「設定・接続」→ `GET /settings` がない（`PATCH` のみ）。同意の一覧参照もない。
- 要件側: `REQUIREMENTS.md` に認証・セッション・CSRF・Origin検証の要件IDがない。verification-register は TEST-SEC-001 を REQ-AI-001（ツール許可リスト）・REQ-KB-001（Vault境界）・REQ-OPS-002（監査）に結び付けているが、これらは認証要件ではない。認証の境界を扱う ISSUE-015 には、受入基準を持つ要件が存在しない。
- 期待: 認証を担う要件IDの追加と、上記routeの定義（またはそれを不要とする設計判断の明記）。
- 影響: 実装者がAPI契約に無い部分を即興で決めることになり、設計が最も慎重に扱うべき境界（認証・CSRF）が仕様の外に出る。
- 検査器が見逃した理由: `check_design.py` は「文書で言及されたrouteが定義済みか」を見る（M4 で確認）が、「画面が必要とするrouteが存在するか」「要件が存在するか」は見ない。

### CR-04（Medium・検査器の穴・再現済み）registerの「実装許可・運用受入」フラグが、他の記録と突き合わされない

- 再現: `verification-register.json` の `application_implementation_authorized=true`、`runtime_acceptance=accepted` に書き換えただけ（試験はすべて `not_run`、`review-state.json` は `implementation_authorized=false` のまま）で、`check_design.py`・`check_review_gate.py` とも **PASS**（M7）。
- 根拠: `check_review_gate.py` は state の `implementation_authorized` が `false` であることを強制するが、register の同名フラグとは照合しない。`check_design.py` は register 内の整合（実行結果に実装許可が要る等）しか見ない。
- 影響: CI の2つのゲートは、パッケージが最も強く掲げる「DESIGN ONLY」の不変条件を、register 側では守らない。偽造された試験結果と組み合わせれば（M1/M2 は証拠欠落で検出されるが、体裁を整えれば通る余地がある）、受入済みの記録を作れる。
- 改善案: 両ファイルのフラグ一致を検査する。`runtime_acceptance` が `accepted` のときは全該当試験が `passed` かつ証拠参照ありを要求する。
- 補足: M3（意味の反転）・M6（承認者の偽装）は検出されないが、どちらも検査器自身が「内容の正しさ・承認の真正性は証明しない」と明記している。ここでは開示どおりであることの確認にとどまる。

### CR-05（Medium・来歴）審査・ゲートが束縛しているのは古いcommit。最新設計は未審査

- 根拠: `review-state.json` と `active-review.json` の対象は `edcebcc6…`（CR-001後）。パッケージの最新は `515fbc59…`。その間に追加された CR-002 の中核文書（`EXECUTION_CONTRACTS.md`、`CONTENT_PRESENTATION.md`、検査器の書き換え、ADR-018）は、README 自身が認める通り Codex の再審査を受けていない。`check_review_gate.py` の PASS は「古い審査記録の改ざんがないこと」しか意味しない。
- 補足: README_DOWNLOAD は 95件の Actions 実行概要の収録を述べるが、内訳は成功18・失敗77。失敗は main と初期ブランチ（検査スクリプト追加前）に集中し、最新 commit の4回は成功。`main` は検査スクリプトを持たないまま赤い状態で、PRはすべて未マージ。誤りではないが、利用者が読み落としやすい。
- 期待: 最新commitに対する審査記録、またはゲートが「審査対象と最新commitが異なる」ことを警告として出す。

### CR-06（Medium・整合）「P0は初期縦断実装の対象」と、絞り込んだ最初の実装範囲が両立しない

- 根拠: `REQUIREMENTS.md` は冒頭で「P0は初期縦断実装の対象」とし、27要件中 P0 は23件（バックアップ、失効の直列化、評価、最小費用上限を含む）。`PRD.md` は「一つの縦断ストーリー」を優先し、`NEXT_STEPS.md` は絞った初回範囲を推奨する。どのP0要件が最初のスライスに入るかを示す追跡表がない。
- 影響: 1人の開発者が単一の Mac 用に作る前提で、リース/フェンシング、失効のepoch、副作用台帳、最終送信envelope、バックアップmanifest を同時に求める読み方ができてしまう。範囲の判断が実装者に委ねられる。
- 改善案: TRACEABILITY に「最初のスライスに含む/後回し」の列を追加する。

### CR-07（Low）評価の標本数では、想定する効果を検出できない

- 根拠: `GROWTH_EVALUATION.md` は評価セットを「20〜100の架空例」とし、「独立問題系列ごとの信頼区間」を必須表示とする。最小効果幅は「holdout実行前に固定」とされるが値がない。
- 計算（Wilson 95%区間、成功率50%のとき）: n=20 で [0.30, 0.70]（半幅±0.20）、n=50 で ±0.13、n=100 で ±0.10。n=20 では、記憶の有無で20ポイント前後の改善が出ても区間が重なる。
- 影響: 「改善が確認できなければ価値仮説を見直す」という判断基準が、標本数の面で機能しない可能性。ペア比較で検出力は上がるが、一致しない組の数に依存し、文書はその見積りを持たない。
- 改善案: 検出したい最小効果と必要系列数を、実験前に算出して固定する。

### CR-08（Low）文言の不明瞭な箇所

- `API_CONTRACT.md`「キーはoperation監査保持期間より短く削除しない」は、「保持期間より前に削除しない」の意図と読めるが、文として曖昧。保持期間が未決の間は実運用不可、とも書かれており、実害は小さい。
