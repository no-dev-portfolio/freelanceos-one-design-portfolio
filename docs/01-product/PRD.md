# DOC-01 製品要求仕様書 — PRD

**版:** 0.10 / **Owner:** Product / **Status:** Proposed

## 1. プロダクトの約束
ITフリーランスの実務を進め、その経験から検証可能な技術・業務知識をObsidianへ育て、次回業務の品質改善を数値で示す。競合する機能の寄せ集めではなく、仕事→検証→知識→再利用の閉ループを提供する。

### Jobs to be Done
- SQL移行・障害調査で、既存の失敗や正しい手順を探し、同じ誤りを防ぎたい。
- 日々の仕事をAIへ委任したいが、勝手な送信やナレッジ破壊は防ぎたい。
- 自分の技術実績を事実に基づいて整理し、案件応募資料の作成につなげたい（後続段階）。

### 主要ペルソナ
P-01: 日本国内の一人ITフリーランス、DB/SQL・VBAの実務経験が豊富。MacでObsidianを利用。公開クラウドへ顧客データを送信したくない。案件獲得と継続学習に時間を使いたい。特定個人の情報に依存しない設計。

### 解決しないこと（初期）
複数組織のマルチテナント課金、AIによる契約承諾、送金、求人サイトの規約違反取得、無制限の自己修正・自動デプロイ、実本番DBへの自由な変更。

## 2. 一貫した利用ストーリー
1. SQL移行の不一致をチャット／添付から依頼。2. Planを確認。3. Vaultから権限のある検証済み知識を取得。4. 許可された隔離テスト環境で変換結果を検証。5. 根拠と差分を提示。6. 知識候補を生成。7. 承認後にVaultを更新。8. 次の別問題で再利用。9. 記憶有無で効果を測定。

## 3. 優先順位
- **P0:** 今日/仕事/知識UI、初回設定、Vault指定・安全読取、索引・権限、出典付き回答、計画/実行/停止、候補抽出、差分/承認、競合検出、監査、同一モデルによる記憶比較評価、機密タスク用の最小推論経路の能力確認、最小費用上限。
- **P1:** SQL Server/Oracle読み取り専用アダプタ、Excel出力、Skill Playbook、案件評価、ローカルLLMの高度な選択・最適化、iPhone確認UI、費用分析。
- **P2:** SaaS化、外部送信自動化、専用Obsidianプラグイン、複数独立エージェント。

## 4. UX原則
- 3主画面・タスク中心・段階的開示。操作を取り消せると偽らない。
- エラー時には何が成功したかと次の操作を明記。
- AI由来・人確認・実証済みを色だけでなく語句で区別。
- 高リスク更新はプレビュー・承認・差分固定。低価値の通知は集約。

## 5. 成功判定（仮説・基準案）
- 代表タスクの初回操作成功率 ≥90%（初期5名の形成的テストでは達成より問題発見を優先）。
- 高リスクの未承認外部変更0件（テストシナリオ内）。
- 削除済み／失効知識を回答根拠に用いるテスト失敗0件。
- ナレッジありで未見タスクの正答率が改善（改善幅はdevベースライン計測後、holdout実行前に固定、改善しなければ価値仮説を見直す）。
- 承認に必要な人間の時間を測定し、手作業との差を明示。

## 6. 経営判断ゲート
Go/No-Goは `06-quality/VERIFICATION_PLAN.md`。Critical未解決・実機競合PoC未合格・記憶の効果が測定不能なら拡大実装しない。

## v0.10 審査後の提供条件

CR-001の設計候補。P0安全更新とMarkdown本文正本を維持し、未検証writerの適用を提供済みとしない。Cloud default OFF、機密の自動fallback禁止。最小local推論経路は能力PoC・性能/品質判定が必要。成立しなければP0未達としてNo-Goとする。publicデータの同意Cloudは既定値変更ではなく任意profile候補。

初期の価値検証は「架空SQL移行の件数不一致」一つの縦断ストーリーを優先し、業務記録→候補→人確認→検証→再利用までの確認時間を手作業と比較する。複数agent、営業自動化、Cloud展開を足して価値未実証を埋めない。5代表操作は初回設定、依頼/停止、根拠検索、訂正/承認、競合復旧。5名は形成的問題発見であり90%達成の統計的証明ではない。

GoはVERIFICATION_PLANのゲートが正本。Critical未解決はNo-Go、Highは明示的な人間リスク受容と影響範囲隔離なしに通さない。設計改修の保存は設計承認・PoC許可・実装許可を意味しない。

## v0.11 設計仕様と実装後の価値確認

CR-002では派生機密の単調taint、訂正fork、証拠採用によるVerified、非実行text表示を具体化。最初の対象は架空SQL件数不一致の一仕事とし、P1/P2拡張で未実証の価値を埋めない。人間interviewと文書導線の確認計画は [VALUE_VALIDATION](VALUE_VALIDATION.md)。実施者/結果未取得はH-pendingと明記。

成功率/人間確認時間/費用/知識効果の実測は実装後のUX/EVALへ登録し、結果が悪ければPRD/機能/検索/検証導線を再設計する。G5-Dの仕様審査とIの実装許可、G5-Rの運用受入を区別する。今回の依頼は設計改修のみでアプリ実装許可ではない。

## v0.12 初回sliceと成立性（CR-003）

製品仮説の完結は手順7〜9まで必要。S1（安全な読取/候補審査）は技術基盤の部分実装で、単独では閉ループ価値を検証できない。S2で協調書込→別系列の仕事への再利用→記憶有無の比較まで行う。P0は削除せずTRACEABILITYへ段階を明記。read-only自体を製品とするなら人間が別ADRで価値仮説を変更する。

P-01の大半をlocal-onlyと見込み、Cloud可用性を前提にしない。I前にS-WRITER/S-LOCAL/H-VALUEの調査・閾値採用を判断し、S未達では拡大実装せず方式/対象仕事へ戻す。実験/人間採否は未実施。
