# 共通AI作業協定（Codex / Claude Code）

## 使命
アプリ実装を急ぐのでなく、実証可能で使いやすく安全な設計を改善し続ける。提案を反証し、機能削減も歓迎する。成果はユーザーが理解できる日本語で報告する。

## 必読の順序
README → PRD → REQUIREMENTS → SCREEN_SPEC → SYSTEM_DESIGN → KNOWLEDGE_MODEL → VERIFICATION_PLAN → REVIEW_RUBRIC → ISSUES → DECISIONS → REVIEW_LOG。

## 必須ワークフロー
1. **スコープ確認:** 設計変更か実装かを区別。利用者の許可がなければ設計のみ。
2. **批判的レビュー:** 少なくとも利用者価値/UX/機能・DB/AI記憶/セキュリティ/障害・運用/費用の7視点で欠陥を探す。
3. **変更提案:** 目的、根本原因、3つ以上の代替案（現状維持を含めてもよい）、費用、リスク、効果測定。
4. **影響分析:** REQ/SCREEN/API/DB/Knowledge/Agent/TESTの関係先を列挙。
5. **ADRとIssue:** 変更前に設計判断を `DECISIONS.md` へ、未解決を `ISSUES.md` へ追記。
6. **変更実施:** 要件・UI・データ・評価を同時更新。勝手な設計の後退を禁止。
7. **反証レビュー:** 自分の提案が失敗する条件と、旧案が優れる条件を明記。
8. **確認:** `python3 scripts/check_design.py`、整合性レビュー、Review log更新。
9. **引継ぎ:** 次回に必要な確認、設計ゲート、未検証事実を列挙。

## 変更権限
設計ファイルの改善提案・軽微な用語修正・矛盾検出は自律的に行ってよい。P0の削除、正本の変更、外部送信の既定値変更、重要なセキュリティ妥協、実装着手は人間の承認待ちとする。

## 禁止
架空テストを「合格」と書く、根拠のない効果数値を採用する、顧客コードを入力例にする、個人情報を持ち込む、勝手に外部公開する、評価データにテスト問題の答えをリークする、仕様変更をREADMEだけに残す。

## 改善ループ
提案→反証→採否→文書整合→設計ゲート→次のIssueを継続。単にレビュー回数を増やすのでなく、リスクの高い未解決事項から潰す。重大な未検証課題があれば「設計完了」と言わない。

## 2026-10-25 利用者指示に基づく検証段階の補足

仕様審査G5-Dと実装後受入G5-Rを分離する。実装依存の未実証はPOST_IMPLEMENTATION_VALIDATION/verification-registerへ担当・期待値・停止・差戻し先付きで登録し、実装後に試験して設計を改良する。未実装ゆえの未実証を文書改良の終了不能条件にしない。ただし実機合格・安全性確認・人間採用を捏造しない。実装着手は引き続き別の明示許可が必要で、今回実装しない。
