# DOC-14 変更管理・継続改善プロセス

1. Issueを登録し、原因・重大度・再現手順・根拠を明記。
2. `templates/CHANGE_REQUEST.md` で現状維持＋代替案を比較。
3. 非自明な判断はADRに記載。High/CriticalやP0削除は人の明示承認を得る。
4. 要件IDと画面/API/知識/評価を同時に更新。`TRACEABILITY.md`を更新。
5. 反証視点の別レビュー（可能ならCodex→Claude、Claude→Codex）。同一AIによる自己採点だけで終えない。
6. `scripts/check_design.py` と手動整合レビューを実施。
7. `REVIEW_LOG.md` に変更内容、証拠、未解決課題を残す。
8. 次回の担当AIには `handoff/START_HERE.md` から再開させる。

**終了条件:** 改善サイクルは回数でなく、Criticalが0、Highのリスク受容が明示され、PoC/UXの実測証拠が得られたときに該当ゲート終了とする。定期的に使われない機能は削除候補とする。

## v0.10 状態と履歴の補足

改修計画CR-001は影響・比較・採否待ちを先に記録し、元の一次REVIEWを上書きしない。レビュー実施記録、文書改修、文書検査、実機実証、重要ADRの人間受容、設計承認、実装許可を別々に記録する。Highを残す場合はVERIFICATION_PLANのG5に従い人間の明示リスク受容と範囲隔離が必要。Critical未解決はNo-Go。未作成UI試作や未実施PoCは参照だけで完了扱いにしない。

## CR-002の検証時期（現行規則）

利用者指示により、実装しないと確認できない事項は実装後のG5-Rで確認し、結果で設計を改良する。G5-Dは仕様・整合・机上の審査、Iは別の実装許可。上記の過去のG5/終了条件は最終安全性・実運用受入を指し、G5-Dに未実装の動作合格を前提として課すものではない。実装後台帳のnot_run/failedをClosedへ偽装しない。失敗→Issue/ADR→全設計と試験更新→新commit再試験を必須化する。
